# 개발 가이드 (Development Guide) v1.10

> 대상: 프로젝트 개발자 (Claude Code 프롬프트 작성 시 참고 문서)
> 목적: 아키텍처, 기술 스택, 설계 원칙을 정리하여 개발 시 일관성 유지

---

## 1. 프로젝트 개요

X(트위터)의 한국어 검색 품질 문제를 해결하기 위해, 본인 계정의 트윗/리트윗/관심글(좋아요·북마크)을 셀프호스팅 방식으로 아카이빙하고, 다국어(한/영/일/중) 검색이 가능한 자체 검색 시스템을 구축하는 도구.

## 2. 배포 원칙

- **완전 셀프호스팅**: 배포자는 코드만 제공, 각 사용자가 자신의 X API 키, DB, 검색엔진을 직접 설치·운영
- 배포자는 타인의 개인정보·검색 데이터·API 비용에 대한 책임을 지지 않음 (Immich, Paperless-ngx와 유사한 모델)

---

## 3. 전체 아키텍처

```
[X 공식 아카이브(zip, 1회성 초기 임포트)]     [X API (OAuth 2.0 + PKCE, BYOK)]
              ↓                                    ↓ 폴링 (since_id 기준, 5~15분 간격)
              └──────────────────┬─────────────────┘
                                 ↓
                        [백엔드: Node.js/Python]
                                 ↓
                  [DB 어댑터] ─── SQLite(기본) / Postgres(선택)
                                 ↓
        [검색엔진 어댑터] ─── Meilisearch(기본) / Elasticsearch+언어별 플러그인(선택)
                                 ↓
                  [프론트: React + Tailwind] → 모바일 웹뷰
```

---

## 4. 기술 스택

| 영역 | 선택 기술 | 대안 |
|---|---|---|
| 백엔드 언어 | Node.js 또는 Python(FastAPI) | - |
| 프론트엔드 | React + Tailwind CSS | - |
| DB | SQLite (기본) | Postgres (선택) |
| 검색엔진 | Meilisearch (기본) | Elasticsearch/OpenSearch (선택) |
| 외부 API | X API v2 (OAuth 2.0 + PKCE, BYOK) | - |
| 배포/실행 환경 | Docker / Docker Compose | 홈서버(라즈베리파이) + Cloudflare Tunnel, 저가 VPS |
| IDE | VSCode | - |

## 5. X API 연동 설계

### 5-1. 인증 방식
- **OAuth 2.0 Authorization Code + PKCE** (BYOK 모델)
- 각 사용자가 본인 명의로 X 개발자 계정 생성 + 크레딧 충전
- Access Token / Refresh Token은 암호화하여 로컬 DB에 저장 (5-1 보안 항목 참고)

### 5-2. 초기 데이터 임포트 (아카이브 백필)

X API의 트윗 조회 엔드포인트는 **최근 3,200개까지만** 반환하므로, 계정 개설 시점부터의 전체 이력은 API로 가져올 수 없다. 따라서 최초 1회는 반드시 X 공식 아카이브(데이터 다운로드)를 통해 임포트한다.

- **소스**: X 설정 > "데이터 다운로드"로 받은 zip 내 `tweet.js`, `like.js` 등 (수만~수십만 건 규모 가능, 준비까지 X 측에서 시간이 걸릴 수 있음)
- **파싱**: 파일 전체가 하나의 JSON 배열이라 통째로 메모리에 올리면 위험 → 스트리밍 파서 사용 (Node.js: `stream-json`, Python: `ijson`)
- **DB 저장**: 건별 insert 대신 배치(batch) insert (예: 1,000건 단위 트랜잭션)
- **검색엔진 인덱싱**: 건별 API 호출 대신 bulk 인덱싱 사용 (Meilisearch `addDocuments` 배치, Elasticsearch `_bulk` API)
- **리트윗 판별**: 아카이브의 `retweeted_status` 필드 유무 또는 텍스트의 `RT @` 접두 여부로 `posts.relation` 값 결정
- **API 비용**: 0원 (아카이브 임포트는 API를 전혀 거치지 않음)
- **완료 후**: 임포트된 트윗 중 가장 최근 ID를 `sync_state.last_synced_id`에 저장 → 이후 API 폴링은 이 지점부터 시작

### 5-3. 런타임 폴링 로직

초기 임포트 이후, 실제 API 폴링은 "임포트 시점 이후 신규분"과 "일상적인 신규 트윗"만 담당한다.

```
[앱 실행/PC 켜짐]
      ↓
① 재시작 캐치업: sync_state.last_synced_id 기준 "마지막 저장 이후~현재"까지 조회
      ↓
② 실행 중: 5~15분 간격 폴링 반복
      ↓
[종료/절전] → 데이터 유실 없음 (X 서버에 남아있다가 재실행 시 캐치업)
```

### 5-4. 비용 구조 (참고)
- Owned Reads(본인 계정 데이터: 트윗/북마크/좋아요/타임라인): 리소스 1건당 $0.001
- 24시간 UTC 윈도우 내 중복 조회는 1회만 과금
- 개인 사용 규모(하루 10건 안팎)는 월 1달러 미만 수준
- 초기 아카이브 임포트는 API를 쓰지 않으므로 이 비용 구조와 무관

## 6. DB 설계

- **기본: SQLite** — 설치 불필요, 파일 하나로 백업/이식 가능, 개인 사용 규모에 충분
- **선택: Postgres** — 기존 인프라 보유 시, 또는 대규모/다중 프로세스 접근 필요 시
- ORM(Prisma 또는 SQLAlchemy)으로 두 DB를 동일 스키마로 지원하는 어댑터 구조 적용
- `.env`의 `DB_TYPE=sqlite` / `DB_TYPE=postgres`로 전환

## 7. 검색엔진 설계

### 7-1. 어댑터 패턴 (스위칭 가능 구조)

```
검색 인터페이스 (SearchProvider)
  ├── MeilisearchAdapter
  └── ElasticsearchAdapter
```

- 공통 메서드: `indexDocument`, `search`
- `.env`의 `SEARCH_ENGINE=meilisearch` / `SEARCH_ENGINE=elasticsearch`로 전환
- Docker Compose profile 기능으로 선택한 엔진만 실행 가능하도록 구성

### 7-2. 엔진별 비교

| 항목 | Meilisearch | Elasticsearch/OpenSearch |
|---|---|---|
| 한국어 처리 | Charabia 내장 토크나이저(세그멘테이션 위주) | Nori 플러그인 (형태소 분석, 정확도 높음) |
| 설정 난이도 | 매우 낮음, 설치만 하면 자동 처리 | 플러그인 설치 + 인덱스 매핑 설정 필요 |
| 리소스 요구량 | 낮음 (Rust 기반) | 높음 (JVM 기반) |
| 라이선스/비용 | 무료 (오픈소스) | 무료 (Self-managed Basic 라이선스) |

### 7-3. 다국어 지원 (한/영/일/중)

**Meilisearch**
- Charabia 토크나이저가 문서 저장 시 언어 자동 감지 및 처리
- 영어: 공백 기반 기본 파이프라인
- 중국어: Jieba 기반 세그멘테이션 내장
- 일본어: 전용 세그멘테이션 파이프라인 내장
- 한국어: 지원되나 Nori 수준의 사전 기반 형태소 분석은 아님
- **별도 설정 불필요**, 자동 처리

**Elasticsearch**
- 언어별 전용 플러그인 설치 필요:
  - 한국어: `analysis-nori`
  - 일본어: `analysis-kuromoji`
  - 중국어: `analysis-smartcn` (또는 IK Analyzer)
  - 영어: 내장 English analyzer (플러그인 불필요)
- 인덱스 매핑에서 언어별 필드에 analyzer 지정 필요 (예: `text_ko` → nori, `text_ja` → kuromoji)
- **유의사항**: Elasticsearch 버전 업그레이드 시 플러그인도 동일 버전으로 재설치 필요

**설계 반영 사항**
- 트윗 저장 시 X API가 제공하는 언어 코드(`lang` 필드)를 함께 저장
- Elasticsearch 어댑터는 `lang` 필드 기준으로 언어별 필드에 매핑하는 로직 포함
- Meilisearch 어댑터는 별도 언어 분기 로직 불필요 (자동 처리에 위임)

**비용**: 금전적 비용 없음 (모든 플러그인 무료 오픈소스). Elasticsearch는 설정 단계만 늘어남.

### 7-4. 고급 검색 문법 지원 (쿼리 파서)

X(트위터) 스타일의 `from:`, `since:`, `until:`, `lang:`, `is:retweet` 등 고급 검색 문법을 지원한다. 검색엔진 자체가 이 문법을 이해하는 것이 아니라, **앱 레벨의 쿼리 파서가 문법을 필터 조건으로 변환**하여 검색엔진에 전달하는 구조다.

**동작 구조**
```
사용자 입력: "김치찌개 from:hongildong since:2025-01-01"
        ↓
[쿼리 파서] 정규식으로 토큰 분리
  검색어: "김치찌개"
  필터: author_username = "hongildong" AND created_at >= 2025-01-01
        ↓
[SearchProvider.search(query, filters)] → 어댑터가 엔진별 필터 문법으로 변환
```

**문법 → 스키마 필드 매핑**

| 문법 | 매핑 필드 | 필터 방식 |
|---|---|---|
| `from:계정명` | `author_username` | 정확 일치 |
| `since:YYYY-MM-DD` | `created_at` | 이상(>=) 범위 |
| `until:YYYY-MM-DD` | `created_at` | 이하(<=) 범위 |
| `lang:ko/en/ja/zh` | `lang` | 정확 일치 |
| `is:retweet` / `is:reply` | `relation` | 정확 일치 |

**어댑터별 구현 방식**

- Meilisearch: `filterableAttributes`에 위 필드를 사전 등록 필요, `search(query, { filter: [...] })` 형태로 호출
- Elasticsearch: `bool` 쿼리의 `filter` 절에 `term`/`range` 조건으로 결합

**구현 시 유의사항**
- 쿼리 파서는 정규식 기반으로 충분하며 별도 NLP 라이브러리 불필요
- `SearchProvider` 인터페이스의 `search()` 메서드에 `filters` 파라미터 추가 필요 (기존 `indexDocument`, `search` 2개 메서드 시그니처 변경)
- 날짜 파싱은 dayjs 또는 date-fns 등 경량 라이브러리 사용 권장
- 신규 필터(예: 미디어 첨부 여부)를 추가하려면 `posts` 스키마에 해당 컬럼 추가 후 두 어댑터 모두에 매핑 반영 필요

## 8. 실행 환경 (로컬 vs 서버)

| 항목 | 로컬 | 서버(홈서버/VPS) |
|---|---|---|
| 폴링 방식 | 실행 시 캐치업 + 실행 중 폴링 | 상시 폴링 (cron/스케줄러) |
| 외부 접속 | 불필요 | Cloudflare Tunnel 등 필요 |
| 검색엔진 실행 | Docker Desktop, 필요 시 실행 | Docker Compose 상시 구동, 재부팅 자동 시작 |
| 비용 | 0원 | 홈서버(장비비만) 또는 VPS(월 $5~10) |

코드베이스는 로컬/서버 환경과 무관하게 동일. 차이는 스케줄러가 실행될 기회(항상 vs 켜졌을 때만)뿐.

**최초 데이터 임포트(5-2) 시점**: 외부 접속(Cloudflare Tunnel 등) 설정과는 무관한 별개 작업이다. 백엔드 컨테이너가 뜬 직후, 배포 머신에서 직접(로컬 브라우저로) 업로드 가능하므로 외부 접속 설정을 마치기 전에 진행해도 된다 — 순서를 강제할 이유가 없어 별도 의존성으로 설계하지 않음(상세 절차는 `docs/07_사용가이드.md` §5-6).

## 8-1. Oracle Cloud Always Free 실배포 절차 (실제 진행 기록, TODO #20)

홈 PC를 상시 켜둘 수 없어 Oracle Cloud Always Free(ARM, 영구 무료)로 이전하면서 실제로 진행한 절차. 아래 설정값(IP 등)은 전부 예시 자리표시자이며, 실제 값으로 바꿔서 사용할 것.

### 계정 가입 + 인스턴스 생성
1. [cloud.oracle.com](https://cloud.oracle.com) 가입 — 결제 인증 오류가 나면 실물 신용카드(체크카드 아님) + 새 이메일 + 청구지 정보 전부 일치시켜서 한 번에 재시도하는 게 성공률이 높았음
2. Compute → Instances → Create instance
3. Image and shape → Edit:
   - Image: **Canonical Ubuntu 24.04**(표준, Minimal 아님) — ⚠️ **"Oracle Linux"와 혼동 주의**(목록에서 image 항목을 변경하지 않으면 기본값이 Oracle Linux로 되어 있어 실수로 그대로 생성한 적 있음, 생성 후 Image details에서 "Canonical Ubuntu"인지 재확인 필수)
   - Shape → Edit → 상단 **"Ampere"** 탭(기본 탭인 "Specialty and previous generation"에는 없음) → **VM.Standard.A1.Flex** 선택(Always Free-eligible), OCPU/Memory는 2 이하/12GB 이하 권장(2026년 기준 Always Free ARM 할당량이 4 OCPU/24GB→2 OCPU/12GB로 축소되는 정책 변경이 진행 중이라 안전하게 낮은 쪽 기준)
4. Add SSH keys: **"Paste public keys"**를 사용할 것(아래 SSH 키 생성 절차 참고) — ⚠️ **"Generate a key pair for me"는 피할 것**: 이 세션에서 그 방식으로 두 번 생성했으나 둘 다 서버가 공개키를 거부(`Permission denied (publickey)`)하는 원인 불명의 문제를 겪음(브라우저 세션 문제로 추정했으나 재부팅 후에도 재발해 확실한 원인은 못 찾음). 로컬에서 직접 키를 생성해 공개키만 붙여넣는 방식으로 전환 후 정상 해결됨.
5. "Out of capacity for shape VM.Standard.A1.Flex" 오류가 나면: OCPU를 더 낮춰서 재시도 / 여러 번 재시도(특히 새벽 시간대) / 그래도 안 되면 계정을 Pay As You Go로 업그레이드(이 세션에서 이 방법으로 해결됨, Always Free 리소스 자체는 업그레이드 후에도 계속 무료 — 단 **Budget 알림을 반드시 설정**해둘 것, 아래 참고)
6. Advanced options의 Security attributes(ZPR)는 엔터프라이즈 전용 기능이라 빈 채로 둘 것
7. "Estimated cost"에 부트 볼륨 비용이 표시되는 건 Always Free 할인을 반영 안 하는 콘솔의 알려진 표시 버그 — 200GB 한도 내 기본 부트 볼륨이면 실제 청구 안 됨

### SSH 키 생성 (로컬 PC에서, Oracle 콘솔의 자동생성 대신 직접 생성)
```bash
ssh-keygen -t rsa -b 2048 -f <키_저장_경로> -N ""
ssh-keygen -y -f <키_저장_경로>   # 패스프레이즈 프롬프트 없이 바로 공개키가 출력되어야 정상(빈 패스프레이즈 확인)
```
`<키_저장_경로>.pub`의 내용을 인스턴스 생성 화면의 "Paste public keys"에 붙여넣는다.

### Budget 알림 설정 (과금 방지, Pay As You Go 전환 시 필수)
콘솔 → **Billing & Cost Management → Budgets → Create Budget**:
- Budget Scope: Compartment, Target Compartment: root
- Schedule: Monthly
- Budget Amount: **1**(달러, 1센트라도 과금되면 즉시 알림)
- Day of the month: 1(기본값)

이메일 알림이지만 사전 차단은 아니므로, 별도로 Cost Analysis 페이지를 가끔 직접 확인하는 것을 권장.

### SSH 접속 (Windows cmd 기준)
```cmd
icacls "<키_저장_경로>" /inheritance:r
icacls "<키_저장_경로>" /grant:r "%USERNAME%:(R)"
ssh -i "<키_저장_경로>" ubuntu@<public IP 입력>
```
(PowerShell에서도 `icacls`는 동일하게 동작. Git Bash에서는 `chmod 400 <키_저장_경로>`로 대체 가능)

`ubuntu`는 Canonical Ubuntu 이미지 기준 기본 계정명이다. Oracle Linux 이미지라면 `opc`를 써야 하므로, 접속이 안 될 때는 먼저 인스턴스의 Image details에서 실제 OS를 확인할 것.

### Docker 설치
```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
exit   # 재접속해서 그룹 적용
```
재접속 후 `docker compose version`으로 정상 설치 확인.

### 저장소 클론 + `.env` 설정
```bash
git clone <저장소_URL>
cd <프로젝트_폴더>/backend
cp ../.env.example .env
nano .env
```
- `APP_MODE=server`로 변경
- `NODE_ENV`: `.env.example`에 `development`로 남아있을 수 있는데, Dockerfile 기본값(`production`)을 덮어써버리므로 **`production`으로 바꾸거나 이 줄 자체를 삭제**할 것 — `docker compose logs backend`로 `NODE_ENV=development`가 찍히면 반영 안 된 것
- `X_CLIENT_ID`/`X_CLIENT_SECRET`: 로컬 개발 환경의 값을 그대로 재사용(재발급 불가능한 값)
- `X_REDIRECT_URI`: 외부 접속 주소(Cloudflare Tunnel URL 등)가 아직 없으면 일단 비워두고, 터널 설정 후 업데이트해도 무방(OAuth 연동은 아카이브 임포트와 독립적인 후속 작업)
- `MEILI_MASTER_KEY`: 로컬 값 재사용하지 말고 `openssl rand -base64 32`로 새로 생성(환경별로 다른 값을 쓰는 게 보안 원칙)
- `TOKEN_ENCRYPTION_KEY`: **`MEILI_MASTER_KEY`와 생성 방식이 다름** — AES-256용 32바이트를 **hex**로 표현한 64자 문자열이어야 함(base64 아님). 서버에 Node.js가 따로 설치되어 있지 않다면(Docker 안에만 있는 경우) `openssl`로 동일하게 생성 가능:
  ```bash
  openssl rand -hex 32
  ```
- `APP_USERNAME`/`APP_PASSWORD`: 원하는 값으로 설정
- ⚠️ **한 줄에 변수 하나씩, 반드시 줄바꿈해서 입력할 것** — nano에서 붙여넣기 중 줄바꿈이 씹혀서 `APP_MODE=server PORT=3000 ...`처럼 여러 변수가 한 줄에 합쳐지면, `APP_MODE`의 실제 값이 `"server"`가 아니라 뒤의 문자열까지 전부 포함돼버려 `appMode === "server"` 비교가 실패하고 서버 모드 로직(Basic Auth 강제 등) 전체가 조용히 비활성화됨 — 실제로 이 문제로 Basic Auth 없이 공개 노출됐던 적이 있었으므로, 저장 후 `cat -A .env`로 각 줄이 `$`(줄끝)로 제대로 끊겨있는지 확인 권장

### Docker Compose 실행 + 외부 노출 (실제 진행)
```bash
cd ~/<프로젝트_폴더>/docker
docker compose -f docker-compose.yml -f docker-compose.server.yml \
  --profile server-meilisearch --env-file ../backend/.env up -d --build
docker compose -f docker-compose.yml -f docker-compose.server.yml ps
```
`backend`가 `Restarting`을 반복하면 `docker compose ... logs backend --tail 50`으로 원인 확인(대부분 `.env` 필수값 누락/형식 오류).

`backend`에 `ports:` 매핑이 의도적으로 없으므로(보안 설계, `internal` 네트워크로만 접근) 호스트에서 `curl 127.0.0.1:3000`은 원래 실패한다 — 정상 동작 확인은 로그의 `listening on port 3000` 메시지로 하거나, 실제 외부 노출(Quick Tunnel 등) 후 확인한다. `docker compose exec backend curl ...`도 `node:22-slim` 베이스 이미지에 curl이 없어 실패하므로 참고.

**도메인 없이 임시로 빠르게 노출하려면(Cloudflare Quick Tunnel)**:
```bash
docker network ls   # internal 네트워크 실제 이름 확인 (보통 <디렉터리명>_internal)
docker run -d --name cloudflared-quick --network <위에서_확인한_네트워크> \
  cloudflare/cloudflared:latest tunnel --url http://backend:3000
sleep 5
docker logs cloudflared-quick 2>&1 | grep trycloudflare.com
```
- 이 방식은 `CLOUDFLARE_TUNNEL_TOKEN`/`DOMAIN`을 설정하지 않으므로 `validateEnv()`가 공인 노출로 인식하지 못해 **Basic Auth가 자동으로 강제되지 않는다** — `APP_USERNAME`/`APP_PASSWORD`를 수동으로 반드시 채워야 하고, 발급된 주소로 접속해서 **로그인 창이 실제로 뜨는지 눈으로 꼭 확인**할 것.
- `docker run`으로 띄운 `cloudflared-quick`은 `--restart` 정책이 없어 서버 재부팅 시 자동으로 안 살아남는다 — 임시 용도이므로 알고 사용할 것. 도메인 준비되면 `docker-compose.server.yml`의 `cloudflare-tunnel` profile(Named Tunnel, `restart: unless-stopped` 적용됨)로 교체.

### 빠른 재기동 (서버 재부팅 등으로 서비스가 내려갔을 때)

**1. SSH 접속**
```cmd
icacls "<키_저장_경로>" /inheritance:r
icacls "<키_저장_경로>" /grant:r "%USERNAME%:(R)"
ssh -i "<키_저장_경로>" ubuntu@<public IP 입력>
```

**2. 상태 확인**
```bash
cd ~/<프로젝트_폴더>/docker
docker compose -f docker-compose.yml -f docker-compose.server.yml ps
docker ps -a | grep cloudflared-quick
```

**3. backend/meilisearch가 안 떠있으면**
```bash
docker compose -f docker-compose.yml -f docker-compose.server.yml \
  --profile server-meilisearch --env-file ../backend/.env up -d
```
(`backend_data`/`meilisearch_data` 볼륨은 유지되므로 데이터 유실 없음. `restart: unless-stopped` 정책 덕분에 보통은 서버 재부팅만으로도 자동 복구되고, 이 명령은 그래도 안 떠있을 때만 필요)

**4. Quick Tunnel(`cloudflared-quick`)이 안 떠있으면**
```bash
docker start cloudflared-quick   # 컨테이너가 남아있으면 이것만으로 충분
# 컨테이너 자체가 사라졌으면 재생성:
docker run -d --name cloudflared-quick --network <internal 네트워크명> \
  cloudflare/cloudflared:latest tunnel --url http://backend:3000
docker logs cloudflared-quick 2>&1 | grep trycloudflare.com   # 접속 주소 재확인(Quick Tunnel 특성상 매번 바뀜)
```

**5. 문제 생기면 로그부터**
```bash
docker compose -f docker-compose.yml -f docker-compose.server.yml logs backend --tail 50
```

### 아카이브 임포트 시 겪은 문제 (Quick Tunnel 경유 시)

1. **zip에 미디어까지 전부 들어있으면 수십 GB** — X 공식 아카이브를 그대로 올리면 사진/동영상까지 포함돼 용량이 매우 커진다. 이 앱은 `data/tweet.js`(또는 `tweets-part*.js`)와 `data/like.js`만 필요하므로, 미디어 폴더는 빼고 이 파일들만 **`data` 폴더 구조를 유지한 채** 재압축할 것(탐색기에서 zip을 폴더처럼 열어 `data` 폴더 안의 해당 파일만 복사 → 새 `data` 폴더에 넣고 그 폴더째로 압축). 파일을 zip 루트에 바로 넣으면 코드의 경로 패턴(`^data\/tweets?(-part\d+)?\.js$`)과 안 맞아 "tweet.js 또는 like.js를 찾지 못했습니다" 에러가 난다 — `unzip -l <zip>`으로 내부 경로가 `data/...`인지 먼저 확인하면 빠르다.
2. **Cloudflare Quick Tunnel은 요청당 업로드 100MB 제한**(무료 플랜) — 이보다 크면 업로드가 중간에 끊겨 zip이 손상되고, 프론트가 "서버 응답을 해석할 수 없습니다" 에러를 띄운다(Cloudflare가 자체 에러 페이지를 돌려줘서 JSON 파싱 실패). 100MB 넘는 아카이브는 Cloudflare를 거치지 않고 직접 업로드해야 한다:
   ```bash
   # 서버: backend에 임시로 포트 노출(작업 후 반드시 제거)
   # docker-compose.server.yml의 backend: 블록에 추가
   #   ports:
   #     - "127.0.0.1:3000:3000"
   docker compose -f docker-compose.yml -f docker-compose.server.yml \
     --profile server-meilisearch --env-file ../backend/.env up -d
   ```
   ```cmd
   REM 로컬 PC: 새 터미널에서 포트포워딩 연결(접속 유지한 채로 열어둘 것)
   ssh -i <키_저장_경로> -L 3000:127.0.0.1:3000 ubuntu@<public IP 입력>
   ```
   이후 브라우저에서 `http://localhost:3000`으로 접속해 업로드(Cloudflare 전혀 경유 안 함). **완료 후 `ports:` 줄을 반드시 제거**하고 재시작해 원래 상태(backend 호스트 미노출)로 복구할 것.
3. 재시도해도 안전함 — `INSERT OR IGNORE` 방식이라 이전 실패 시도로 일부 데이터가 이미 들어갔어도 중복/덮어쓰기 걱정 없음.

## 9. 보안 설계 (필수 구현 항목)

셀프호스팅 구조상 서버/인프라 보안 사고가 나면 사용자 본인의 트윗 전문·개인정보가 그대로 노출될 수 있으므로, 아래 항목은 "선택"이 아니라 **개발 단계에서 기본값으로 강제**해야 합니다.

| # | 항목 | 위험 | 구현 요구사항 |
|---|---|---|---|
| 1 | 검색엔진 인증 미설정 | Meilisearch 마스터키 없으면 API로 전체 데이터 조회/수정 가능 | 앱 시작 시 `MEILI_MASTER_KEY` 환경변수 존재 여부를 체크하고, 없으면 **실행 자체를 막는 검증 코드** 작성 |
| 2 | Elasticsearch 보안 기능 비활성화 | 기본 설치 시 인증 없이 9200 포트 노출 가능 | `xpack.security.enabled=true` 강제, 최초 실행 시 `elasticsearch-reset-password`로 비밀번호 설정을 요구하는 초기화 스크립트 포함 |
| 3 | Docker 포트가 모든 인터페이스에 바인딩 | `ports: "7700:7700"`처럼 쓰면 0.0.0.0에 바인딩되어 외부 노출 | 로컬 프로필의 `docker-compose.yml`에는 기본값으로 `"127.0.0.1:7700:7700"` 형태로 작성. 서버 프로필은 리버스 프록시(예: Caddy/Nginx) 뒤에만 검색엔진이 위치하도록 네트워크 분리(내부 네트워크만 사용, 외부 노출 포트 없음) |
| 4 | .env / 시크릿 관리 | 실수로 커밋되면 git history에 영구 잔존 | `.gitignore`에 `.env` 포함은 기본, 추가로 pre-commit hook(예: gitleaks)으로 커밋 전 시크릿 스캔 자동화 코드 포함 |
| 5 | OAuth 토큰 평문 저장 | DB 탈취 시 X 계정 접근권까지 노출 | Refresh Token은 AES-256 등으로 암호화 후 저장, 암호화 키는 `.env`의 별도 변수(`TOKEN_ENCRYPTION_KEY`)로 관리, 코드 내 하드코딩 금지 |
| 6 | OAuth CSRF/오픈 리다이렉트 | 공격자가 인증 흐름을 가로챌 수 있음 | OAuth 요청 시 `state` 파라미터 필수 생성·검증, Redirect URI는 화이트리스트 방식으로 정확히 일치하는 값만 허용 |
| 7 | DB 파일 노출 | SQLite 파일이 정적 서빙 경로에 있으면 웹으로 직접 다운로드 가능 | DB 파일 경로를 웹서버 정적 파일 루트 바깥(`/data/archive.db` 등)에 고정, 앱 최초 실행 시 파일 권한을 `chmod 600`으로 자동 설정하는 코드 포함 |
| 8 | 터널 노출 시 인증 계층 부재 | Cloudflare Tunnel 등 공인 URL 방식은 URL만 알면 누구나 접속 가능 | 서버 프로필에는 기본 Basic Auth 미들웨어를 포함시키고, `.env`의 `APP_USERNAME`/`APP_PASSWORD`로 설정하도록 구현. `DOMAIN` 또는 `CLOUDFLARE_TUNNEL_TOKEN`이 설정된 공인 노출 시에는 미설정 시 서버 모드 실행 차단(필수), Tailscale 등 사설 네트워크 전용 노출 시에는 선택(자격증명 없이도 실행 가능, 콘솔 경고만 출력) |
| 9 | HTTPS 미적용 | VPS + 직접 도메인 연결 시 평문 트래픽 노출 | 서버 프로필 Docker Compose에 Caddy(자동 HTTPS) 포함을 기본 구성으로 제공 |

## 10. 프론트엔드 설계

### 10-1. 브랜드 요소 vs UX 패턴 구분

이 프로젝트는 오픈소스 셀프호스팅 배포물이므로, X(트위터)의 브랜드 요소와 UX 패턴을 구분해서 적용한다.

| 구분 | 방침 |
|---|---|
| X 로고, "Twitter"/"X" 브랜드명 | **사용 금지** (상표권 문제) — 독자적인 이름/로고 사용 |
| X 브랜드 컬러(#1D9BF0 등) 그대로 복제 | **지양** — 공식 앱으로 오인될 수 있음, 독자 색상 팔레트 사용 |
| 타임라인 카드 레이아웃, 무한 스크롤 등 UX 패턴 | **참고 가능** — 저작권/상표 보호 대상 아님, 대부분의 피드형 앱이 공유하는 범용 패턴 |

### 10-2. 레이아웃 구조 (검색 중심 설계)

```
┌─────────────────────────────────┐
│  검색창 (from:/since:/until: 지원) │  ← 상단 고정
├─────────────────────────────────┤
│ [전체] [트윗] [리트윗] [좋아요] [북마크] │  ← relation 필터 탭
├─────────────────────────────────┤
│ ┌─────────────────────────────┐ │
│ │ 작성자 · 관계배지(RT/좋아요)  │ │
│ │ 본문 텍스트 (검색어 하이라이트) │ │  ← 카드형 피드
│ │ 날짜 · 원본 링크              │ │
│ └─────────────────────────────┘ │
│              ...                │
└─────────────────────────────────┘
```

### 10-3. 핵심 설계 원칙

- **검색바 상단 고정**: 검색이 핵심 기능이므로 스크롤과 무관하게 항상 노출
- **관계 배지(relation badge)**: `posts.relation` 필드를 카드 상단에 태그로 표시 (트윗/리트윗/좋아요/북마크 구분)
- **검색어 하이라이트**: 검색 결과 카드 내 매칭 텍스트를 강조 표시
- **페이지네이션**: 무한 스크롤 대신 20~30개 단위 "더 보기" 버튼 방식 채택 (커서 기반 페이지네이션 복잡도 회피, 개인 아카이브 규모에 적합)
- **모바일 우선**: 1단 컬럼(single column) 레이아웃 기본, 데스크톱은 중앙 정렬된 좁은 폭으로 동일 레이아웃 재사용
- **언어 필터**: `posts.lang` 필드를 relation 탭과 별도로 필터/드롭다운 형태로 노출

### 10-4. 참고 가능한 레퍼런스

- 타임라인 카드 구조: X, Bluesky, Mastodon (범용 패턴, 자유롭게 참고)
- 검색 중심 UI: Notion 검색, GitHub 코드 검색 (필터 태그 + 하이라이트 조합)

```markdown
# 프로젝트: 트위터 다국어 아카이빙 도구

## 아키텍처 원칙
- 완전 셀프호스팅
- DB: SQLite 기본 / Postgres 선택 (어댑터 패턴)
- 검색엔진: Meilisearch 기본 / Elasticsearch 선택 (어댑터 패턴)
- 다국어 지원: 한/영/일/중 (언어 필드 기준 매핑)
- 고급 검색: from/since/until/lang/is 등 X 스타일 문법을 앱 레벨 쿼리 파서가 필터로 변환 (검색엔진은 필터링만 담당)
- 데이터 수집: 최초 1회 X 공식 아카이브(zip)로 전체 이력 임포트(스트리밍 파싱+배치 insert+bulk 인덱싱) → 이후 API 폴링(since_id 기준, 5~15분 간격)으로 신규분만 수집
- X API: OAuth 2.0 + PKCE, BYOK

## 보안 필수 사항
- 검색엔진은 인증 설정 없이는 실행되지 않도록 검증 코드 필수
- OAuth 토큰은 반드시 암호화 저장, state 파라미터 검증 필수
- 서버 모드에서 공인 노출(도메인/Cloudflare Tunnel)일 경우 Basic Auth 또는 앱 로그인 없이는 실행 차단, 사설 네트워크 전용 노출이면 선택
- .env, DB 파일 등 민감 파일은 커밋/외부 노출 금지 (pre-commit 시크릿 스캔 포함)

## 컨벤션
- 커밋 메시지는 한국어로 작성
- API 키/시크릿은 .env에만 저장, 코드 하드코딩 금지
- 새 기능 추가 전 계획을 먼저 설명하고 승인받은 뒤 구현
- 되돌리기 어려운 작업(파일 삭제, DB 스키마 변경)은 항상 확인받기
- 프론트엔드에서 X 로고/브랜드명/브랜드 컬러를 그대로 복제하지 않음 (UX 패턴만 참고, 독자 브랜드 요소 사용)
```

## 12. 개발 우선순위 (진행 순서)

1. Docker / Docker Compose 기초 인프라 구성 (보안 기본값 포함: 포트 바인딩, 네트워크 분리)
2. X API OAuth 2.0 연동 (state 검증, 토큰 암호화 포함)
3. 백엔드 CRUD API 구현 (DB 어댑터 포함)
4. 초기 아카이브 임포트 파이프라인 구현 (스트리밍 파싱, 배치 insert, sync_state 부트스트랩)
5. Meilisearch 연동 (마스터키 강제) → 기본 검색 기능 구현 (bulk 인덱싱 포함)
6. 어댑터 패턴 확장 → Elasticsearch(보안 기능 활성화 포함) + 언어별 플러그인(Nori/Kuromoji/SmartCN) 연동
7. 다국어 필드 매핑 로직 구현 (lang 필드 기준)
8. 고급 검색 쿼리 파서 구현 (from/since/until/lang/is 문법 → 필터 변환, SearchProvider.search()에 filters 파라미터 추가)
9. Docker Compose Profile로 로컬/서버 배포 스크립트 정리 (서버 프로필에 Basic Auth, Caddy HTTPS 기본 포함)
10. Cloudflare Tunnel 외부 접속 구성 (서버형)
11. pre-commit 시크릿 스캔(gitleaks 등) 설정
12. 프론트엔드 구현 (검색바 고정, relation 필터 탭, 카드형 피드, 검색어 하이라이트, "더 보기" 페이지네이션) — 독자 브랜드 요소(이름/색상/로고) 적용
